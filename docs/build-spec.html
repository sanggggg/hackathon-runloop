Five traps we already stepped in

Each of these cost real time to diagnose. Read them before writing the engine.

01

Session cookies do not live in the browser profile

A cookie with no expiry is held in memory only. Fork a devbox, relaunch the browser from its profile directory, and every branch is logged out. This killed the first working version.

ctx.storage_state(path=…) before the snapshot · new_context(storage_state=…) after the fork
02

A disk snapshot does not carry processes

Files come across; the running app does not. Every forked box starts with nothing listening on the port.

restart the app in each fork before driving the browser
03

execute_sync is deprecated, and backgrounding hangs it

Launching a long-running process with & leaves the output pipe open, so the API call itself never returns. The process is fine; your client is stuck.

POST /devboxes/{id}/execute_async for anything long-lived
04

download_file takes path, relative to home

Not file_path, and not absolute. An absolute path returns 400 with no useful message.

{"path": "work/shots/step2.png"}
05

pip needs sudo; the browser binary must not have it

pip install writes to /usr/local and fails as the devbox user. But installing Chromium as root puts it in /root/.cache, where the user cannot find it — Playwright then insists you run playwright install, which you just did.

sudo pip install · sudo playwright install-deps · playwright install (as user)

Engine — how a run walks the tree

The orchestrator does a depth-first walk. The rule that keeps it fast is simple: snapshot only at nodes with two or more children. A straight run of single-child steps stays on the same devbox, so a deep-but-narrow tree costs one snapshot, not one per step.

walk(node, box):
  kids = tree.childrenOf(node)

  // leaf — judge and stop
  if kids.length == 0:
     verdict = judgeScreen(box, node.intent)
     record(node, verdict); shutdown(box); return

  // single child — stay on this box, no snapshot
  if kids.length == 1:
     step(box, kids[0]); walk(kids[0], box); return

  // real fork point — this is the only place we snapshot
  snap = snapshotDisk(box)
  parallel for kid in kids:
     child = createDevbox({ snapshot_id: snap })
     restartApp(child)                  // trap 02
     restoreStorageState(child)          // trap 01
     step(child, kid)
     walk(kid, child)
  shutdown(box)

step() is where the agent lives. It never replays a stored selector — it re-resolves the intent against the page every time. That is the whole reason a renamed control reads as passed · UI changed instead of a false failure.

The rule that makes agent QA affordable

Wall clock tracks tree depth, not path count. Eight paths at depth three finish in the time of the slowest single branch — about 16 seconds — instead of eight sign-ins back to back. Every design decision downstream protects this property.

Pinned contracts

These are the interfaces that let the work split. Pin them first, then nobody blocks on anybody. Changing one of these mid-build is the only thing that can stall the whole team.

Suite & tree

What the Build route produces and the Run route consumes.

Suite {
  id, name
  repo:     { url, ref, buildCmd, startCmd, port }
  blueprintId                // image with deps + browser baked in
  fixture:  { snapshotId, ref, description }
  tree:     Node[]
}

Node {
  id
  parentId    // null = the fixture root
  label       // short human name on the card
  intent      // the sentence the agent resolves — never a selector
  expectedOutcome? // what a healthy terminal screen should prove
  kind:  'fixture' | 'step' | 'goal'
  state: 'unverified' | 'verified' | 'unresolved'
  lastSeenLabel?   // what the control read last time it resolved; a hint, not a bypass
}

state is tree health, not run outcome. unresolved means the wording matched nothing on the page — a bug in the tree. A path that resolves fine and then lands on an error screen is a bug in the app, and that shows up in the run, not here.

Run & results

Run {
  id, suiteId, ref
  startedAt, finishedAt
  fixtureSnapshotId
  results:    NodeResult[]
  discovered: Node[]   // options seen during the run that the tree did not have
  modelCalls?          // successful structured model responses; independent of billing
  costUsd, wallClockMs, sequentialEstimateMs
}

NodeResult {
  nodeId
  status: 'pass' | 'fail'          // the only two the tree is coloured by
  note?:  'ui-changed' | 'new-path'
  failReason?: 'unresolved' | 'error-screen' | 'timeout'
  resolvedTo?  // human description of what it matched, e.g. '"Use a starter" card'
  screenshotId
  modelCalls?  // successful structured model responses for this node
  devboxId
  elapsedMs    // cumulative after devbox creation; includes prepare + straight-path work
  log: { t: number, text: string, level: 'info'|'warn'|'error' }[]
}

Agent calls

Two, with deliberately different budgets. Element picking runs on every step and must be a narrow classification — hand it the candidates and make it choose one. Screen judging runs only at leaves and gets the open-ended question.

resolveIntent({
  candidates: { ref, role, name, text }[],   // from the accessibility tree
  intent:     string,
  hint?:      string                          // node.lastSeenLabel
}) → { ref, confidence } | { ref: null, reason }
   cheap model, temperature 0, structured output

judgeScreen({
  title, visibleText, url, expected: string   // expectedOutcome, or intent fallback
}) → { ok: boolean, reason: string }
   capable model, leaves only

Setup

prepareRepo({ url, ref, buildCmd, startCmd, port, testAccount? })
  → { blueprintId, fixture: { snapshotId, screenshotId } }

Order of operations

Only the first item is genuinely blocking. After it, work in parallel and integrate against mocks.

  1. Write the two schemas into a file Suite/Node and Run/NodeResult, committed. Thirty minutes, and it unblocks four people. blocking
  2. Build the Blueprint Chromium, Playwright and the app's deps baked into an image. Removes 41 seconds from every experiment for the rest of the night. do early
  3. A and B in parallel, against mocks The orchestrator can run with a stub resolver that returns the first candidate; the resolver can be scored on saved pages with no devbox.
  4. D and E against fixture JSON Hand-write one Suite and one Run as JSON files. Both UIs can be finished before the engine returns anything real.
  5. Join A and B, run against F First real end-to-end. Expect the first run to be mostly red — that is the system working, not failing.
  6. Two commits, two runs Run against the whole commit, then the broken one. This is the demo. the payoff

Demo script

Three minutes, four beats. The app lives inside the devbox, so the second commit can be checked out live on stage.

  1. Paste a GitHub URL Clone, build, sign in, fixture captured. One field, and the audience sees where every branch will start from.
  2. Say what to cover, in a sentence "Cover signup and onboarding, skip anything that charges a card." Eight grey cards appear. Nothing has run.
  3. Run against the first commit One snapshot, eight devboxes, sixteen seconds. Point at the wall-clock bars: three and a half minutes of sign-ins collapsed into one.
  4. Run against the second commit Two reds where paths broke. One green that says passed · UI changed — a renamed button the agent followed anyway. One green that says new path, which the tree never knew about. Then the closing line: a stored selector would have failed all four.

If something has to be cut

Cut the Build route before anything else and hand-write the tree JSON. The run against two commits is the demo; everything else is framing.
